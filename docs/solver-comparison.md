# Solver comparison for the Bronze reference

This is a prototype, not a production optimizer. Run `cargo run --manifest-path solver-comparison/Cargo.toml --locked` and `cargo test --manifest-path solver-comparison/Cargo.toml --locked`. It uses the exact domain and assumptions in [requirements](specs/optimization.md#exhaustive-bronze-reference-domain): three ordered slots, each empty or clean 1Lz, at least one jump, at most two, with an optional exclusion of 1Lz. Each jump contributes 60 hundredths. The independent reference validates candidates and looks up base values; the prototype compares all solver results to it and to a separate fixed fixture.

On Windows x86-64, Rust 1.99.1, Pumpkin 0.5.0 and z3 crate 0.22.0, both returned 120 and the same three pairs of occupied slots; excluding 1Lz was infeasible. Pumpkin optimizes the count, then iterates solutions with that optimum fixed until the iterator reports finished. Z3 maximizes the count, proves that a larger count is unsatisfiable with a separate solver, then blocks each assignment until unsatisfiable. Thus `optimal_proven` and complete enumeration are separate results. These proofs cover only this encoded model, not complete ISU compliance. All matching candidates are validated and scored by the reference.

The executable stops on unknown, interruption or a non-optimal Pumpkin result instead of claiming a proof. `feasible_unproven` means an incumbent exists without an optimality proof; `incomplete/timeout` means the search or enumeration stopped before proof, with or without an incumbent. Neither case was exercised here. Pumpkin exposes distinct optimal, satisfiable, unknown and stopped results and a termination condition; Z3 exposes unknown and supports timeouts. Z3 optimization `sat` alone is not treated as an optimality proof here. The prototype does not yet return partial results or implement time limits. Infeasible is reported only on a solver contradiction or unsatisfiability result. External proof certificates and interruption handling were not independently checked.

## Integration and decision

Pumpkin is implemented in Rust and has a native Rust API, but the 0.5.0 dependency graph requires at least Rust 1.95; it built with Rust 1.99.1. Its iterator and optimization API require explicit model construction, brancher, resolver and termination handling. Z3 requires native libraries; the Rust binding's `gh-release` feature downloaded a platform-specific binary during the build. Vendoring compiles native Z3 with CMake. This creates build, deployment and cross-compilation costs. Neither solver was built for WebAssembly; Pumpkin's Rust implementation alone does not prove browser compatibility, and Z3's native dependency makes that target a separate integration task. Repeated-run determinism, interruption and larger workloads were not measured. No performance conclusion follows from eight assignments.

Select **Pumpkin for the next bounded native prototype**, not as a production commitment. It avoids a native Z3 runtime dependency and produces the same results on this instance. Reassess the toolchain version, WASM build, deterministic behavior and interruption semantics before integration. Keep the exhaustive reference as an oracle and avoid a solver framework until a concrete caller needs one. OR-Tools was not evaluated: these two solvers covered the modeled feasibility, optimum and enumeration cases, and this tiny instance gives no basis for a broader comparison.
